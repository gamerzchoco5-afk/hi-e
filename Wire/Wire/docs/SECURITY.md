# Security design

## Credentials and recovery

Passwords use Argon2id with 64 MiB memory, three passes, two lanes and at most two simultaneous password operations in each main worker. Passwords and request bodies are never logged. Password input is bounded and weak/repeated passwords are rejected. A dummy hash is verified for unknown accounts. Login and password-sensitive mutations lock the account row to serialize with recovery and avoid issuing a session from a stale password verification. Separate IP and account limits cover login/recovery attempts.

Sessions are random 256-bit opaque values, with only SHA-256 digests in Postgres. Sessions expire, are capped per account and are checked against live records by the chat and account endpoints. Logout, password reset and account deletion do not depend on stale client JWT claims. Email addresses, dates of birth, hashes and recovery codes are not included in public profiles.

Recovery codes have 128 random bits each. Their hashes are bound to the account. Password recovery atomically consumes one matching code and revokes old sessions in the same transaction. Code replacement requires the current password and replaces all old hashes. The setup screen blocks screenshots and stores any unacknowledged screen state encrypted with Android Keystore; acknowledgement removes it. Codes are not re-downloadable from the backend.

Email challenges expire after 10 minutes, are single-use and are stored as keyed HMAC hashes. The main service requires a secret pepper and a working STARTTLS SMTP configuration in production. Production never automatically verifies an email.

## Authorization and database

All protected requests check the current session, disabled state, account restriction and email verification. Ownership/membership checks cover profiles, social mutations, chat requests, messages, reports and read positions. Counts and ownership come from the database; clients cannot assign badges, post authors or follower counts. Unknown payload properties are rejected.

Every application table is in a private schema with RLS enabled. Only dedicated backend roles have access. The chat role cannot select credential or recovery columns; the main role cannot query chat messages. Neither role can create roles/databases, bypass RLS or act as a superuser. No app table is granted to Supabase's public client roles. The project administrator can explicitly assume the restricted service roles for permission tests and maintenance; it does not inherit those memberships automatically.

Foreign keys and unique constraints protect identity uniqueness, relations, conversation participants and request idempotency. Account deletion cascades into both domains. SQL values are parameterized. Database logins have statement, lock and idle transaction timeouts.

## Requests and media

The body boundary handles chunked input, applies an absolute body-read budget and rejects oversized/non-JSON writes. Validation errors do not echo password input. Request IDs and security response headers are generated by the server. Shared atomic database limits enforce IP, account and action budgets across workers. A separate rate-check connection pool prevents nested pool starvation during concurrent authenticated requests.

The hybrid app client bounds queued work and response sizes, applies connection/read deadlines, persists cooldowns and cancels pending work when a screen stops. It stops dispatching additional API calls during a server-directed cooldown. This is a client behavior guarantee, not a defense against a modified client: requests already transmitted may still reach a server, which independently enforces access checks and limits.

Profile-photo decoding is limited to two concurrent operations. Uploads are capped, decoded only as JPEG/PNG/WebP, pixel-bounded, stripped of metadata and re-encoded. SVG, HTML, animated images and arbitrary uploaded files are rejected. The dependency lock includes a patched Pillow release and package hashes.

Pasted URLs are never fetched by the backends, preventing URL-preview SSRF there. Media loading is explicit and restricted to supported providers. The YouTube player is a sandboxed cross-origin iframe with no access to the app or its credentials, and disallows local file/content access and mixed content. Ordinary app screens use native Views. The APK contains no database password, SMTP password or Supabase secret key.

## Device and deployment

Session tokens and pending recovery-screen data use AES-GCM under Android Keystore keys (a small native plugin, WireVault). Backups/device transfer are excluded. Traffic is HTTPS-only, uses native HTTP with normal certificate validation, has a fixed API origin baked in at build time, and disables WebView debugging. Sign-in, recovery and password screens block screenshots (FLAG_SECURE).

The supplied reverse-proxy template accepts forwarded client IPs only from one configured proxy address. Runtime containers use different database logins, non-root users and a read-only filesystem. Public deployment still needs actual TLS endpoints, an SMTP sender, a verified database connection, backups, monitoring, a moderation process and the owner's signing key.

Tests and dependency/advisor results cover specific checks and versions at delivery. They do not establish that software is impossible to compromise or that every device, provider, hosting failure or future vulnerability has been exercised. Chat is not end-to-end encrypted. No independent penetration test or public-internet load test was performed.
